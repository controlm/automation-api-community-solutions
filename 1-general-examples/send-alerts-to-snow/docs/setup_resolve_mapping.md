# setup_resolve_mapping.py

One-time (well - "run it every time you edit the mapping") setup helper.
Written specifically so the person maintaining routing rules never needs to
know ServiceNow concepts like `sys_id` or the Table API. Belongs entirely to
the incident pipeline - the job report pipeline has no routing/mapping
concept at all.

## Who runs this, and when

Whoever has ServiceNow access - not necessarily the Control-M admin. Run it:

- Once, during initial setup
- Any time `config/mapping_source.json` changes (new Application prefix,
  renamed group, etc.)

## What it does

1. Reads `config/mapping_source.json` - plain ServiceNow names only:
   ```json
   {
     "service_name": "Secure Data Transfer Service",
     "pattern": "ZZM*",
     "assignment_group_name": "Secure Data Transfer",
     "cmdb_ci_name": "Secure Data Transfer Service"
   }
   ```
2. Authenticates to ServiceNow (reuses `get_oauth_token()` from
   `ctm_to_snow_incident.py` - not a separate, potentially-drifting copy of
   the same logic).
3. For each rule, looks up the assignment group name against `sys_user_group`
   and the Business Service name against `cmdb_ci_service_business`
   (reusing `lookup_sys_id()`, same import).
4. Writes `config/mapping.json` - the **same** names, plus the resolved
   `sys_id` for each, plus a `_do_not_edit` marker record as the first
   array entry.

## Reading the output

Plain-English status per rule, no ServiceNow jargon required to interpret:

```text
Rule 1: pattern='ZZM*'
  [OK] Assignment group 'Secure Data Transfer' found.
  [OK] Business Service 'Secure Data Transfer Service' found.
```

If a name doesn't exist in ServiceNow:

```text
  [NOT FOUND] Assignment group 'Some Typo' does not exist in ServiceNow.
              Check the spelling against ServiceNow's Groups list and try again.
```

A `[NOT FOUND]` entry doesn't block the other rules - `mapping.json` is
still written, just with a blank sys_id for that specific field, and the
script exits with code 1 so the failure is still detectable in automation.
Fix the name in `mapping_source.json` and re-run.

## Ambiguous name matches

If a name matches more than one ServiceNow record, `lookup_sys_id()` uses
the first result and logs a warning - it does not fail. Use a more specific
name in `mapping_source.json` if this happens (check the console output;
it logs which sys_id was chosen).

## Why the group/CI lookups are one-time, not live

The incident pipeline's runtime script (`ctm_to_snow_incident.py`)
intentionally does **not** look up names at alert-processing time - that was
tried and reverted during development. Doing a live ServiceNow lookup on
every single alert adds an HTTP round-trip (and a real-time failure mode) to
the hot path, for something that only needs to happen once, whenever the
mapping actually changes. This script exists specifically to move that cost
out of the per-alert path.

## The `_do_not_edit` marker

`mapping.json`'s first array entry is a sentinel object, not a routing rule:

```json
{
  "_do_not_edit": true,
  "_note": "This file is auto-generated by setup_resolve_mapping.py...",
  "_generated_at": "2026-07-23T05:12:44.123456"
}
```

`ctm_to_snow_incident.py`'s `load_mapping()` filters this out specifically
by checking for the `_do_not_edit` key - not by checking for a missing or
empty `pattern` field, which would be unsafe (see that script's own doc for
why). Don't remove this marker or repurpose the key name without updating
the filter on the other side.

## Note on file naming

`config/mapping_source.json` (checked in with the demo `ZZM* -> Secure Data
Transfer` rule plus a `*` catch-all) is the file this script reads and the
one you edit for real routing changes. `config/mapping.json` is generated
from it and is gitignored - never edit that one by hand.
